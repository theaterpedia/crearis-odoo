## details 
### new odoo module
To separate essentials of the agenda_lines implementation from options and to isolate future enhancements we introduce a separate module 'crearis_milestones'. If installed the module adds the config option use_milestones to company.

### the 'current' part or the 'inner phase' of the event-workflow / event-lifecycle

### three quite simple agenda-lines bring the idea to life
In short I see 3 default non-session-lines per event that either are added to the agenda or are connected to it: info-mail | opening-reminder | wrap-up.
They are much like the workflow that we originally designed around the 'meldefrist', but they are smaller in weight. The most important thing on this: With 'use_milestones' they are all (including) the 'meldefrist' connected to advancing the stage of the event (the parent-event, not the session-line)!! I think we completely left that untouched in the basic conception of agenda-lines, right? 
If we assume that those 3 non-session-lines somehow are connected to advancing the event-stage then a lot of interesting options arise.

Let me first list-out and specify those default agenda-lines or otherwise workflow-processes, then map them onto the event-stages.

### framing the 'hot' event through 3 interactions
3 rather small interactions/lines make up the 'hot' phase of an event. This only applies to events (not sub-sessions of events) that have an in-presence-part and additionally the event fits one of these rules:
- either the event is standalone (customers registered explicitely, often only to this one event like a 'workshop'-registration)
- or is at least 6hours long (if part of a package or a course)

**a: info-mail**: is a comprehensive Email to be sent 10-30 days prior to the event, typically with added or updated information on both content (preparational infos, download-urls) + organisation (for instance: "watch-out: hotels-booking in Munich is complicated around the dates of the event")
**b: opening-reminder**: is typically small, max. has minor updates on organisation-details (parking-information), typically provides exact information on how the instructor is reachable (-> don't overimplement here, just consider it to understand the modeling -> post-v1-implementation)
**c: wrap-up**: typically comes 1-2 days after (for short events like 4hours-workshop) or 1-2 weeks after the event (for multi-day like 'block') -> before sending it some work has to be done, for instance participants have to finish a protocoll. Then the instructor writes a summary, typically with links and references, further recommendations

### event-stages extend the hot phase of an event, bring in 'early controlling' as another topic for the 'current'-window of event-management
Now lets consider the stages of the event that are fully under odoo-control, they extend the "live"-phase beyond "hot" and thus help to model the main part of the event-lifecycle: this main cycle starts after transitioning from planning to 'announced', it ends when a 'closed' event is being archived (for instance because the course is closed that needed access to the event).

**These 4 stages build the main part of the event-lifecycle:** (compare to dev_docs_quick_reference)

As we sync from sharepoint (or on other companies: have done similar preparational planning), events are in 'draft'. If the 'meldefrist' is passed successfully the event advances to 'announced/confirmed'.
Then together with sending the 'info-mail' the event is 'current/released', meaning that all information is 'localized into the details'.
The wrap-up email is being sent to announce that the event is 'closed/completed', typically no additions to be expected to event-documentation anymore.

The 'hot' phase typically only spans 3-5 weeks, it spans from 2-3 before the date_begin of an event until 1 week after date_end. It opens when the event transitions to released/current and closes with the transition to completed.
The only other point to be considered else is the 'when-is-the-milestone'-question? It is the taget-date where the management wants to transition the event from draft to confirmed. In order to do so it needs sufficient registrations. In our field of work this only partly is a question of numbers. As soon that a minimum of 'reservations' is reached it is a question of the quality of those reservations. Therefore in the 7-14 days prior to the milestone some kind of coordinated effort runs to gather quality feedback on the intent of really participating. This is the 'confirmation phase'. 
Apart from those 2 phases 'confirmation' and 'realisation' the event is more or less 'dormant' but typically sits in the database for 5-10 years because every now and then it is part of a report, website export or whatever action that lists or inspects the event.

### What are milestones?
So to finally define it: What are milestones, how to implement them?
Milestones are additional dates that can be added where typically or latest the stage has to be advanced. A milestone typically needs human verification, thus: a decision
The existing fields date_begin, date_end, 'milestone' provide the milestones, but if we see a milestone-date as the date where the transition of the event stages happens, then always an offset has to be added to the date: Typically these are the values: 
- a) `-14 days after 'milestone'` = event advances to 'confirmed/released'
- b) `-14 days to date_begin` = event advances to 'current'
- c) `+ 7 days after date_end` = event advances to 'completed'
So, I think this is the default-logic that should be provided by 'crearis' module already.

If we look into it we see:
1. sometimes we have pre-milestone, sometimes post-milestone logic > so lets call the connected agenda-lines "frontrunner", "follower": So the b) 'transition-2-current'-milestone is a 'frontrunner' to 'date_begin'
2. the "opening-reminder" seems to be forgotten

With the 'frontrunning' and the 'following' some things are set in stone, cannot be changed, on others we should take a good decision. This decision has effect on the 'crearis'-module and only gets extended in the 'crearis_milestones' - module: 
- we cannot shift date_begin or date_end -> so we should inspect how frontrunning and following has to be implemented from there
- but even with date_begin and date_end we have a minor consideration to be confirmed again: dasei established the convention that if we have in-presence sessions on an event combined with 'frontrunning' and 'following' online-session-lines that  date_begin and date_end are the dates of the in-present-sessions and the online-sessions have to be found prior and after that
- interesting is the question whether to have a) 'milestone' define the 'start-date' of the 'confirmation phase' or the 'end-date' of this phase. Or could it even live in the middle of it, that for instance: first inquiry and evaluations happens, then the milestone itself=decision-point and then follower-actions -> confirmation-emailing + eventually action-chaining (a whole 'product' getting confirmed because the first milestone of the first event is being confirmed)
