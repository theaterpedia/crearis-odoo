**Why adding the meldefrist date-field makes sense, how to make use of it and why to not add even more date-fields?**
While the 'meldefrist' allows to hard-set distinct controlling and makes it easy to implement against it, for the other transitions it typically would be over-implementation to add even more distinct date-fields.
Instead they typically follow a broader schedule of the organisation or the individual instructor or a customer-company (for in-house-bookings).
Best would be to simply have the ability to forecast upcoming automations and have the ability to front-run them. 
If there is no good option how to detect this, I think this could be a good option for a transient model that has a distinct purpose of enabling to forecast the next 4 weeks + gives an interface to adjust trigger-dates
edge-case to be considered here are after-the-trigger bookings: I am pretty sure that odoo has this captured already with default implementations (had seen this in practice I think): already processed triggers being rerun if a new attendance is registered on the event

Instead of having to batch-together multiple confirmations into a single email (or as preparation for a later implementation of such a feature) it would be perfect to allow for all agenda-line and events related triggers to have a central configuration per company that controls when on the day those triggers are being processed. It should be a time-window of 1 hour and optimally does not fall into the 'main' business hours. So the company can choose whether agenda runs 'evening' or 'morning' notifications. Morning 07:00-08:00. Evening 17:00-18:00.
If we have a transient model at work here this would allow for things like a managing-role at the company at 14:00 could be alerted some hours before the notification-batch about what kind of information will be processed, allowing to quickly add in additional details.

So I think we should consider how this gets implemented:
- either a fourth 'provider' of agenda.lines: The 'system' (called 'odoo-bot' for now). A cycle like for instance the 3-months-cycle could be configured on that level, basic defaults that typically only run in the background could be surfaced.
- or it means that the 'transient model' I am thinking about is a separate service not to be confused with agenda-lines but can be mixed in somehow, or that the transient model extends the agenda-lines and mixes in system-lines?
- If we have the option to either configure this against company or against  domaincode it would allow for a lot of flexibility with these 3 options:
	- default
	- bi_weekly: every second week on a given day + time a meeting gets scheduled with all of the instructors of the events for the next 5 weeks, if they log in to the system they can access the UI to see all relevant lines. This could be filtered (or something similar: ordered // or at least: highlighted): 'only my lines', 'only next 14days', 'only next 3 days', 'only online-sessions', 'only info-lines'
	- monday_wednesday: at monday 09:00 + wednesday 14:00
	- the whole system works on agenda-lines
	- but typically filters out (+3 more badge) subsequent in-presence-lines for the same or the next days, if they are all in a row
	- as soon as there are missing days in between, the line should be added
	- all online-sessions  are being added
	- whether other lines are added or not, is to be decided (specified, can be hardcoded, mostly without of config-options)
	- there will some few info-lines crucial to be editable (like to allow to quickly update details for the parking around the location of an event -> this could be a 'type/mode')
	- but the most infos only need to be 'reachable' (for instance: Hoverable)
	- actions, milestones most probably only need to be 'reachable', because otherwise this could heavily lift the complexity -> everything that would again trigger automations should need to be excluded from simplified Updating through the mechanisms, needs to be accessed in the root-view
	- Implementation should be desktop/tablet-first and -> we add a task on how to make this mobile-compatible for post v1-launch
