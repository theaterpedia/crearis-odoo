	- We clearly separate long-lasting documents and long-lasting document-structure from other documents that only have snapshot-character, important only in the context of action-plans and sprints.
	- The long-lasting-documents slowly build up a whitepaper and are not date-prefixed and do not have 'devdocs' in the filename. 'Devdocs' are intermediary. They hold long-lasting information, but less organized, do not follow a standardized terminology and are not being systematically audited. They are typically created on-the-fly towards the end of implementation and help to capture and index reached status.
	- The whitepaper itself is one single entry-point-document called 'index.md'. This only lists chapters. Each chapter is an index-document prefixed with 'chapter_' that has this simple structure: title + abstract + links-table to the master documents that form the chapter. The links-table is organized with 5 cols Title/link, description, stage, notes, version. Version is left empty for the moment, we will start to put code-versions there. The status-column only knows fives stages: task -> draft -> dev -> spec -> user. The 'master documents' don't have a file-naming-convention. They simply should NOT start with date, 'devdocs', 'chapter'. They have a header-section that gives a clear status of the document, prominent are: type: 'master' + stage: one of the 5 stages. Those documents may freely be converted from 'master' to 'details' or the other way round. Only from inside type 'master' or 'detail' documents we build links to other documents, like for instance sprint-documents prefixed with date or 'devdocs'-prefixed documents. We do not build a lot of backlinks, where devdocs or sprint-docs reference the whitepaper. Since the whitepaper continuously advances this would mean a lot of constant fixing of refs, deprecating and so forth. It is better to simply use the terminology like 'session-lines' -> once the whitepaper has a basic structure it is easy to understand where the session-lines are being laid out, often the better approach to assume 're-researching needed' than simply relying on outdated refs. The master-docs-staging follows an 'append stage-by-stage' approach: First we try to create a task-chapter. This stays at the top of the document and can be frequently updated to reflect current status. Once we advance to draft we add a '## draft' section to the doc and have a lot of room to freely draft. Once we advance to dev or spec -> the draft-content gets reviewed, simplified and will start serving as text-only abstract. Dev is selective with code-examples + often UI-imagery, Spec is 'complete' (not like 'api' fully complete, but has all major patterns captured), User is written in German and targets the end-user.
	- under chat we have the folder 'files': these are source-file-examples from other systems, images. They are organized in batches/packages by subfolders. This way it is possible to keep the original filenames.
	- The whole idea is to turn the whitepaper into md-driven static docs (like mkdocs or vitepress) some day and to run this more or less from one folder to make linking as easy as possible and independent from specific file-systems.
